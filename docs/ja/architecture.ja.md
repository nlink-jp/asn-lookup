# asn-lookup アーキテクチャ

本書はツールが「なぜ」この形なのかを説明します。使い方は
[README](../../README.ja.md)、運用上の要点は [AGENTS.md](../../AGENTS.md) を参照。

## 目的

ipinfo API を繰り返し叩かずに、対話的・AI 駆動の用途に耐える速度で、次の 2 つを
ローカル・オフラインで答える:

1. **IP → AS**: あるアドレスの所属 ASN（と国/大陸）は？
2. **AS → IP**: ある ASN が広告するプレフィックスは？

## なぜ IPinfo Lite か、そしてなぜ MMDB を使わないか

IPinfo は無料の **IPinfo Lite** を MMDB / CSV / JSON / Parquet で配布しています。
MMDB は「アドレス → データ」の一方向にのみ最適化されています。2 つめの要件
（ASN → プレフィックス）は*逆*引きであり、IP キーの MMDB では木全体を走査せずに
は答えられず、ASN ごとのプレフィックス列挙も容易ではありません。

逆引きのためにどのみち生の CSV を取り込む必要があるため、MMDB を使う利点は
消えます。CSV を解析してしまえば前方参照も同じデータから賄えるからです。そこで
本ツールは CSV を取り込み、両方向を賄う**単一の索引**を構築します。副次的な利点
として、`net/netip` による CSV 解析はサードパーティ製ライブラリを必要としない
ため、バイナリは**外部依存ゼロ**になります（`nlk` / `mcp-guardian` と同じ流儀）。

## 索引

`update` は gzip 圧縮の Lite CSV をストリーム処理し、コンパクトで自己完結した
索引ファイルを構築します:

- **レコード** — AS/geo 属性（`asn, as_name, as_domain, country, country_code,
  continent, continent_code`）を重複排除します。数百万のネットワークがはるかに
  少ない distinct なレコード集合に畳まれ、インデックス参照されます。文字列は
  単一テーブルにインターンします。
- **前方参照エントリ** — 各ネットワークを `(start, prefix-bits, record)` に変換し、
  IPv4 テーブル（`uint32` の start）と IPv6 テーブル（`[16]byte` の start）に分け、
  それぞれ start アドレス昇順でソートします。

オンディスク配置は「小さなヘッダ + 文字列テーブル + レコードテーブル + v4/v6
エントリ配列」で、すべて固定幅です。`Open` はファイル全体を一度メモリに読み込み、
型付き配列にスライスします。

### 前方参照（IP → AS）

Lite DB は分割（partition）であり、ネットワークは重複しません。よってアドレスに
対し、ファミリ別のソート済みエントリを二分探索して `start ≤ addr` の最大要素を
見つけ、その候補プレフィックスが実際にアドレスを `Contains` するか確認します。
含まなければ未割当のギャップ → not found。`O(log n)` 1 回、アロケーションなし。

### 逆引き（AS → IP）

ASN キーの second index を持たず、`LookupASN` は前方参照エントリを**走査**して、
レコードの ASN が対象と一致するものを集め、`(start, bits)` から各プレフィックスを
再構成します。帰結は 2 つ:

- **ドリフトしない。** 逆引きの答えは前方参照が使うのと同一のエントリから導出
  されるため、両者が食い違うことはあり得ません。
- **メモリ削減。** 重複する構造を構築・保持しません。

走査は `O(n)` ですが、数百万エントリでもミリ秒で完了し、対話/MCP セッションが
たまに行う逆引きには十分です。将来逆引きスループットが問題になれば、前方参照に
触れずにソート済み ASN 索引をファイル形式へ追加できます。

## レイヤ構成

```
asndb   ── 純粋な索引: parse / build / open / lookup（io.Reader/Writer 以外の I/O なし）
config  ── 設定解決（TOML サブセット + env + フラグ）
ipinfo  ── Fetcher インターフェース（+ HTTP 実装）; ダウンロードをモック可能に
engine  ── LoadDB / Update（アトミック）/ IsStale — 共有ユースケース
app     ── CLI シェル（dispatch, コマンド, 出力整形）
mcp     ── stdio JSON-RPC 2.0 サーバー; 同一 engine をツールとして公開
workspace ─ エージェント指定の出力先 + os.Root 書き込み封じ込め
```

**engine** が CLI と MCP サーバーの唯一の合流点であり、update や鮮度ロジックの
変更が両方に適用されます。ダウンロードは `Fetcher` インターフェースの背後にあり、
`engine` とコマンドはネットワークなしでテストできます。シリアライズはソースの
タイムスタンプを引数で受け取るため、索引構築は決定的でテスト可能です。

## 大きな結果のファイル経由伝送

逆引きは非有界です。1 つの ASN が数十万の Lite ネットワーク行に対応し得ます
（Cloudflare は約59万件、大半が地理分割された IPv6）。これを MCP ツールでインライン
返却すると AI のコンテキストを溢れさせます（数十MBのJSON）。素朴なトランケートは
答えの大半を黙って隠してしまいます。

そこで `lookup_asn` は voice-studio-mcp のファイル経由方式を採用します。常に
コンパクトなサマリ（`prefix_count`/`v4_count`/`v6_count`）+ インライン preview を
返し、全件が `limit` を超える場合は一覧をファイルに書き出してパスのみ返します
（`prefixes_file`, `truncated: true`、および全件数 — 黙って隠すことはしません）。

設計上の要点は 2 つ:

- **出力先は呼び出し側が指定。** Cowork のような強サンドボックスでは、サーバーは
  エージェントが許可した場所にしか書けません。よってワークスペースはハードコードした
  `$HOME` 配下ではなく、**エージェントがリクエストごとに伝達**する必要があります
  （`workspace_root`）。利便のためのサーバー既定もありますが、サンドボックス安全な
  経路はエージェント指定パスです。
- **書き込みは封じ込め。** エージェント書き込み可能なワークスペースには symlink が
  仕込まれ得ます。全書き込みは `os.Root`（`internal/workspace`）を通し、カーネルが
  強制するため、symlink 経路でワークスペース外へ書き出すことはできません。字句的な
  事前チェックで絶対パスや `..` を先に弾き、分かりやすいエラーにします。葉のファイル名
  はサーバー生成なので呼び出し側は制御しません。

`lookup_ip` はインライン維持です。出力は呼び出し側が渡す入力リストに比例するため、
爆発しません。

## セキュリティとプライバシー

- ipinfo トークンは秘密情報です。エンドポイントが規定するクエリパラメータ（および
  `Authorization: Bearer` ヘッダ）で送られますが、エラーやログに現れる URL は
  必ず `ipinfo.Redact` を通してから出力します。
- 照会はオフラインであり、照会対象アドレスに関する情報はマシンから外へ出ません。
